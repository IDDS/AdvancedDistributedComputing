## 一、审查结论

总体结论：课件已经形成“模型 → 时间/全局状态 → 消息序 → 算法 → 云原生/AI 应用 → 共识/一致性 → 安全与系统综合”的完整主线，内容量足以支撑 17 周研究生课程。当前没有发现会导致 XeLaTeX 失败、未定义控制序列、缺字或未定义引用的致命问题。

严格覆盖结论需要区分两层含义：

- 2025 课件的主要主题、定义、公式、算法、证明要点、例图语义与讨论题，已经在中文重编版中建立覆盖；
- 本版不是逐字翻译或逐帧复制。原课件中连续动画、重复 build 页和大段英文说明被重组为中文静态过程图、时间线和解释页，因此页数与文字量不能直接一一比较。

本轮按“信息单元是否保留”而不是“是否有同名标题”重新审查，确认并修复了此前存在的细节压缩问题。修复后未再发现 2025 课件中的独立知识主题被整段遗漏；但仍不宣称与原文件像素级、逐句级等价。

## 二、逐章专业意见

### 第 1 章：概述

- Send/Receive 四类时间线基本正确，但“异步 Send”应明确是教学抽象，避免学生把它与 MPI 的 buffered/synchronous/ready send 模式一一对应。
- 建议在首次出现“透明性、开放性、可扩展性”时各给一个反例，避免只停留在定义层。

### 第 2 章：模型

- 可靠、有限但无已知上界的基础模型与后面允许丢失/崩溃/Byzantine 的扩展要显式分层；所有算法页最好带一行“本算法假设”。
- `Causal ⊂ FIFO ⊂ Non-FIFO` 只能解释为“满足保证的执行集合包含关系”，课上应反复强调这一点。
- `happens-before`、`happened-before` 建议统一为一个术语。

### 第 3 章：逻辑时钟

- 本轮已经修正向量时钟错误等价式：单个自身分量只能做必要条件或快速筛选，不能推出因果；完整结论必须使用全分量偏序。
- 矩阵时钟更新规则建议在讲义备注中给出“知识的知识”定义，并说明是否采用全矩阵合并还是仅更新接收行。
- NTP 公式在对称单向延迟假设下正确；工程延伸建议区分 wall clock 与 monotonic clock，并说明 leap second/校时 step 对超时的影响。

### 第 4 章：快照

- Chandy–Lamport FIFO marker 部分完整且例子正确。
- Mattern 部分已标为教学化版本；正式授课时不要把“未来向量时间 + dummy”当作无需额外终止证据的完整实现。
- Acharya–Badrinath 的 `约 2n` 消息、2 个传输时间单位只适用于特定的完全互连/可靠因果交付/中心收集模型，已在源码中限定，课上还应口头提醒。

### 第 5 章：算法与图算法

- Bellman–Ford 例子正确；源码已明确本例使用无向图，但算法可推广到有向图。
- GHS 章节实际讲的是同步 Borůvka 风格教学版本，不是标准异步 GHS 的完整 level/phase 协议；复杂度只能标为“本页同步简化模型”，不能直接作为标准 GHS 复杂度结论。
- LCR 的 `O(n)` 时间依赖可靠单向环和按跳计时；异步网络的实际墙钟时间还受消息延迟影响。

### 第 6 章：实验与复杂度

- 生成树、同步器和实验设计结构良好。
- 建议每个实验表格固定增加四列：网络模型、故障模型、消息大小、停止条件；否则学生容易把“轮数”误报成“端到端延迟”。

### 第 7 章：消息序与组播

- 已修复 RST 交付条件中的数学符号；源码现在写成 `\forall x,\quad ...`。
- 应统一强调 arrival、receive、application delivery 是三个不同时刻；因果广播只约束 delivery 语义。
- RST/向量摘要例子默认可靠信道、无故障、发送者单调编号，已补入页面说明。
- Total Order 中央 sequencer 例子需要补一句“sequencer 故障/重启需 epoch 或共识接管”。

### 第 8 章：Kubernetes

- 控制面、声明式 reconcile、Pod/Service/存储/多租户主线完整。
- 原有因果链图已修复重叠并通过图像复核。
- 新增 Kueue/Volcano 类 GPU 队列与 gang scheduling 案例；建议讲授时将“队列准入”和“Pod 实际启动”分成两个状态机。
- 新增三页 PD（Prefill/Decode）分离：明确 P/D 独立资源池、KV block 传输与版本校验、取消/回退/epoch/fencing，以及 TTFT、TPOT 和队列指标；它是典型架构抽象，具体 RPC/RDMA/共享存储实现需按系统区分。
- `watch` 应补 resourceVersion、断线 relist、事件压缩/过期等边界；Pod IP 也应注明是普通 Pod 的默认网络模型。

### 第 9 章：终止检测

- 权重投掷例子和守恒不变量清楚。
- 已补充可靠送达、精确计数/去重和检测期间无崩溃的前提；否则重复控制消息会复制权重，丢失消息会永久吞掉权重。
- “权重投掷”是教学性 credit/weight 方案名称，建议在参考文献页标注所对应的经典算法或明确写成“credit distribution family”。

### 第 10 章：分布式互斥

- Lamport、Ricart–Agrawala、Maekawa、Suzuki–Kasami、Raymond 的比较链条完整。
- Suzuki–Kasami 页已明确当前简化记号假设每个站点至多一个未完成请求；若课堂要讨论多个并发请求，必须改写为序列区间/请求队列。
- Maekawa 的 `3√N` 仅适用于方形 quorum 设计和特定消息统计；Raymond 的公平性也依赖树形和调度策略。

### 第 11 章：死锁与全局谓词

- 已补充 CMH probe 的基础正确性模型：可靠信道、无崩溃、等待边仍可验证；实际丢包和故障要另加重传、epoch 和故障检测。
- “死锁是稳定谓词”必须限定在封闭计算、无取消/抢占/恢复/外部释放的语境；源码已增加限定。
- OR/AND-OR 模型不能只用简单环判定，课堂例子应保留 knot/闭锁集合的反例。

### 第 12 章：检查点与回滚

- orphan/lost/delayed/duplicate 分类、协调/非协调/日志恢复比较和训练恢复线完整。
- 新增 PyTorch Distributed Checkpoint/FSDP 案例，强调 rank 分片、元数据、重分片恢复和 manifest 原子提交。
- Koo–Toueg 处应明确当前是“二阶段协调思想”，不是完整协议伪代码。

### 第 13 章：故障检测器

- 已将类别改为标准 `P、S、◇P、◇S`，并说明 `◇S` 中“最终”只修饰 accuracy。
- 轮换协调者例子把“估计值”和“已锁定/已决定值”放在一起，建议在正式版本中单独标记 `estimate`、`locked`、`decide` 三种状态，避免学生误以为任意最高轮次估计都可以覆盖已决定值。
- Kubernetes 的 Running、Ready、Lease 应继续作为独立信号讲授，不要画成线性状态机。

### 第 14 章：共识与一致性

- Raft 复制、当前任期提交、旧 leader 恢复和 Paxos 多数派交集例子基本正确。
- 应补充 Raft 成员变更的 joint consensus，及“旧任期日志通过当前任期 entry 间接提交”的限制。
- Paxos 讲授时要反复区分 accepted、chosen 和 learned；本页例子已经体现多数派 chosen 不可改，但术语可再加一行定义。
- 新增 etcd/Raft 控制面案例，强调 watch/relist 和 reconcile loop 与共识日志的分工。

### 第 15 章：DSM 与一致性

- Linearizability、sequential consistency、causal consistency 的例子逻辑正确。
- 写失效流程是教学协议，不是所有 DSM/缓存系统的统一实现；应明确“租约/版本/失效确认”是本例选择。
- 新增 Flink checkpoint barrier 与 watermark 案例，明确 barrier 是状态恢复边界，watermark 是事件时间进度，二者不能互相替代。

### 第 16 章：认证与安全

- nonce 重放例子、Kerberos 三段式、mTLS、RBAC/ABAC、AI 供应链内容完整。
- 数字签名页已修正“不可否认性”过强表述；应继续强调签名不等于授权。
- Kerberos 初始登录图是教学简化版，正式课上建议补 AS-REQ/AS-REP、TGT、TGS-REQ/TGS-REP 的标准字段。
- 新增 SPIFFE/SPIRE 工作负载身份案例，适合连接 workload identity、短期凭证和自动轮换。

### 第 17 章：P2P、自稳定与综合

- Chord 查找、finger、churn、CAN/Tapestry、自稳定 token ring 和 AI 映射完整。
- Dijkstra 例子已采用中心 daemon；本例 4 个节点取 `K≥4`，一般版本应写成“状态空间大小至少满足算法所需的 `K≥n` 条件”。
- CAN 的 multiple realities 已改成“多套独立坐标空间”，避免学生把 reality 误解为普通副本。
- 新增 Ray/KubeRay 案例，强调控制面元数据、worker 重启、epoch、幂等结果和外部 checkpoint 的边界。

## 三、近期应用案例的教学编排建议

| 应用案例 | 对应概念 | 建议课堂追问 |
|---|---|---|
| Kubernetes + etcd/Raft | 共识、watch、relist、reconcile | watch 断线后为什么必须 relist？ |
| Kueue/Volcano 类 GPU 队列 | gang scheduling、配额、公平、抢占 | 7/8 张 GPU 时如何避免作业占位？ |
| 大模型 PD 分离 | Prefill/Decode 资源解耦、KV 传输、流控与故障恢复 | Decode 池缩容时先保护 TTFT、TPOT 还是 GPU 利用率？ |
| PyTorch DCP/FSDP | 分片 checkpoint、manifest、重分片恢复 | worker 数变化后如何恢复同一训练步？ |
| Flink barrier/watermark | 全局快照、流处理进度、迟到数据 | watermark 到了但 checkpoint 未提交时能否发布？ |
| SPIFFE/SPIRE + mTLS | workload identity、凭证轮换、零信任 | 身份证明和授权策略如何解耦？ |
| Ray/KubeRay | 控制面/数据面、对象引用、重试与 epoch | 旧 worker 如何被 fencing？ |

这些案例都应以“先写系统模型，再写状态不变量，再讨论性能”为固定讲法，避免把产品 API 当作算法证明。

## 四、交付前最后一轮建议

1. 每一章开头增加一页“本章模型合同”：进程、信道、时钟、故障、可靠性、终止条件。
2. 每一个复杂度数字后面加括号标注“同步/异步、拓扑、消息大小、是否含恢复控制流”。
3. 每一个完整算法例子都补一个失败分支：消息丢失、重复、延迟、节点崩溃或网络分区至少选一种。
4. 第 14–17 章建议用一条贯穿学期的 AI 模型发布案例串起来：训练 checkpoint → 注册中心共识 → GPU 队列准入 → mTLS 身份 → P2P/缓存分发。
5. 课堂互动材料应要求学生写出“安全性、活性、假设”，而不只回答“哪一个组件负责”。
