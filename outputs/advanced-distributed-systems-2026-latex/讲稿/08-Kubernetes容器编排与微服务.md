# 第 8 讲：容器编排、Kubernetes 与微服务

## 一、本讲定位

本讲从容器交付链进入 Kubernetes 的控制系统。学生应理解：容器解决打包和隔离，编排系统解决期望状态、调度、故障恢复、网络、存储和升级。

## 二、容器与编排

### 1. 容器解决了什么

容器把应用、依赖和启动命令打包，利用操作系统内核提供进程、文件系统和资源隔离。它减少环境漂移，但不自动解决多节点放置、服务发现、故障重启、滚动升级、数据持久化和跨节点网络。

### 2. Docker 交付链

把 Dockerfile、镜像仓库、运行时串成一条链：

构建镜像 → 推送仓库 → 节点拉取 → 创建容器 → 暴露端口 → 记录健康状态。

追问：镜像中没有配置密钥时，运行时如何注入？答案是环境变量、Secret、挂载卷或外部配置服务；配置和镜像生命周期需要分离。

## 三、Kubernetes 控制面与数据面

### 1. 组件职责

- API Server：认证、校验、对象入口和 watch；
- etcd：持久化一致的集群状态；
- Scheduler：为未绑定 Pod 选择节点；
- Controller：观察期望/实际差距并采取动作；
- Kubelet：在节点上执行 Pod 生命周期；
- 容器运行时：拉镜像、创建和停止容器。

讲控制面图时强调箭头方向：用户不直接命令每台机器；用户提交期望状态，控制器和 kubelet 逐步收敛。

### 2. kubectl apply 时间线

1. 用户提交 YAML；
2. API Server 做认证、准入和 schema 校验；
3. 对象写入 etcd；
4. Controller watch 到变化；
5. Scheduler 绑定 Pod 到节点；
6. Kubelet 拉镜像并启动容器；
7. 状态回写 API Server 和 etcd；
8. Service/Endpoint 根据 Ready 状态更新后端集合。

这条时间线是后面所有 Kubernetes 例子的主线。

## 四、Pod 与 Service

### 1. Pod 为什么是最小调度单位

需要共享 localhost、网络命名空间、卷和生命周期的容器应该放入同一 Pod。文件拉取器和 Web 服务就是典型例子：一个写共享卷，一个读共享卷。

强调 Pod 不是永久身份：

- 节点故障后原 Pod 不会在另一节点保持相同 UID；
- 新 Pod 得到新的 IP 和运行时状态；
- 稳定访问应交给 Service、StatefulSet 或外部存储。

### 2. Service

Service 把可替换 Pod 集合抽象为稳定入口。标签选择器、Ready 条件和端点更新共同决定请求是否进入某个后端。客户端不应自己维护全部 Pod 列表。

## 五、ReplicaSet 与控制环

控制器反复做三件事：

1. 读取期望副本数；
2. 观察当前 Ready Pod；
3. 通过创建/删除动作缩小差距。

如果期望为 4、实际 Ready 为 3，动作是创建 1 个 Pod；如果某个 Pod 退出，下一次 watch 又会触发修复。控制器不依赖“上一次做过什么”，而依赖当前状态，因此更容易恢复。

## 六、滚动升级

### 1. maxSurge 与 maxUnavailable

以 replicas=6、maxSurge=2、maxUnavailable=1 为例：

- 先创建最多 2 个新 Pod；
- 新 Pod Ready 后进入 Service；
- 再摘除旧 Pod、排空连接；
- 重复直到旧版本为 0、新版本为 6。

强调：没有 Ready，不能继续删除旧 Pod；这就是升级中的可用性不变量。

### 2. 回滚

若新版本一直不 Ready，Deployment 应暂停或回滚。回滚不是把时间倒回，而是把期望状态改回旧版本，控制器再次执行收敛。

## 七、PV、PVC 与存储

管理员提供 PV 或 StorageClass，用户提交 PVC，控制器匹配容量、访问模式、拓扑和性能，再由 Pod 挂载 PVC。

解释四种状态：

- Available；
- Bound；
- Released；
- Reclaimed。

提醒学生：删除 PVC 不等于数据已经删除，真正结果取决于 reclaimPolicy、快照和底层存储。

AI 训练要区分对象存储、共享文件系统、本地 NVMe 和元数据存储：

- 对象存储：数据集、权重、归档；
- 共享文件系统：多 Pod 读取；
- 本地 NVMe：shuffle、缓存、临时检查点；
- 元数据存储：作业状态和版本。

## 八、微服务网络与可观测性

服务调用就是程序控制流的一部分。一次请求跨越多个服务后，必须传播 trace/span、请求 ID 和超时预算。

重试的危险：

- 一个局部慢服务触发上游重试；
- 重试增加请求量；
- 队列变长导致更多超时；
- 最终形成级联故障。

课堂中要求学生画出一次请求的调用图，并标记每个可能失败点。

## 九、AI 基础设施映射

- GPU Pod：调度原子性和拓扑感知；
- 推理 Deployment：副本、Ready 和滚动升级；
- 模型权重：PV/PVC 或对象存储；
- KV Cache：易失、热点、需要路由感知；
- PD 分离：预填充和解码副本的协同；
- KubeRay：控制面提交任务，数据面执行对象和任务。

强调 Kubernetes 不是自动解决 AI 调度，而是提供控制环骨架；GPU 拓扑、显存、模型缓存和通信带宽仍需额外调度器理解。

## 十、课堂互动

1. 给一份 YAML，要求学生指出期望状态和实际状态；
2. 推演一次 kubectl apply；
3. 设一个 Pod NotReady，判断哪一层移除它；
4. 给 Rolling Update 参数，预测每一步副本数量；
5. 判断某个训练 checkpoint 应使用哪一类存储。

### 收束句

> Kubernetes 的本质不是“更复杂的 Docker 命令”，而是把集群变成一个可编程控制系统。用户声明目标，控制器观察差距，节点执行动作，状态再反馈回来。

## 十一、控制面和数据面的边界

Watch 客户端必须记录 resourceVersion；断连、版本过期或事件压缩后要重新 list，再从新版本继续 watch。Service 提供稳定入口，但不保证请求命中持有 KV Cache、GPU 显存或会话状态的实例。Pod Ready 只表示可以接收流量，Job Completed 只表示控制器观察到完成；checkpoint、数据提交和外部副作用仍需应用协议确认。PD 分离是架构模式，不是 Kubernetes 自动提供的语义，路由、缓存生命周期和重试幂等仍要单独设计。
