# 第 7 讲：消息顺序、同步消息与组通信

## 一、本讲定位

本讲回答三个层层递进的问题：

1. 消息以什么顺序到达和交付？
2. 如何在异步系统中模拟同步 send？
3. 如何把点到点顺序扩展为组内共同顺序？

核心术语包括 FIFO、因果顺序、CO、RSC/SYNC、crown、binary rendezvous、RST/KS、全序组播、传播树和 Steiner tree。

## 二、消息顺序

### 1. FIFO 不足以保持全局因果

先用两个发送者举例：

- P1 发送 a 给 P3；
- P2 收到 a 后发送 b 给 P3。

P3 可能先收到 b。虽然每条信道内部 FIFO，但跨信道因果被破坏。

因此要区分：

- per-sender order；
- FIFO channel order；
- causal order；
- total order。

### 2. 四类 source–destination 关系

开放组通信中：

- SSSG：单源单组；
- MSSG：多源单组；
- SSMG：单源多组；
- MSMG：多源多组。

关系越复杂，传播树和排序点越难设计。不要把四类关系当作命名题，要问源、组成员和目的集合分别是否变化。

## 三、Crown 与 RSC

### 1. 同步重放的困难

同步程序的 send 只有在对应 receive 配对后才算完成。异步 runtime 若直接重放，可能出现：

- P1 等 P2 的 ACK；
- P2 等 P3 的消息；
- P3 又等 P1 的消息。

这就是等待环。

### 2. Crown test

把每条消息 M=[s,r] 看成顶点。若 s(M) 先于 r(M')，就在 M→M' 之间连边。若得到有向环，就存在 crown。

判定流程：

1. 列出所有 send/receive 对；
2. 计算每条消息的 send 和 receive 事件；
3. 对满足 s(M) < r(M') 的消息对连边；
4. 运行拓扑排序或环检测；
5. 有环则不是 RSC，无环则可按某种顺序重放。

强调：crown 是消息间的结构，不是某个单独进程的局部环。

### 3. RSC 的时间戳刻画

如果给 send 和 receive 赋予同步时间戳，要求同一消息两端时间一致；对非消息因果关系，时间严格增加。这样可把“无 crown”转为时间函数存在性问题。

## 四、Binary Rendezvous

### 1. 为什么需要优先级

让每个进程都等待对方，会产生对称死锁。Bagrodia 思路是用优先级打破对称：

- 高优先级发送给低优先级：直接发送 M，等待 ACK；
- 低优先级发送给高优先级：先发送 request(M)，得到 permission 后再发送 M。

阻塞依赖沿优先级方向排列，因此不能形成环。

### 2. 完整事件规则

1. SEND 到低优先级：send(M)，阻塞至 ack(M)；
2. SEND 到高优先级：send(request(M))，等待 permission(M)；
3. 收到低优先级 request：发送 permission；
4. 收到高优先级 M：执行 receive(M)，返回 ACK；
5. 解阻塞后按队列继续处理。

课堂上画两个进程的双向发送，让学生判断哪一方先 request、哪一方直接 send。

## 五、RST、KS 与因果组播

RST/KS 的重点是：消息不能交付，直到它的因果前驱已经被目标进程交付。用 DELIV 向量描述每个目的地已经交付到哪里。

讲交付条件时，要求学生逐项检查：

- sender 分量是否恰好是下一条消息；
- 其他分量是否不超过本地 DELIV；
- 若不满足，消息进入 buffer；
- 前驱到达后重新检查。

这与向量时钟直接相连：发送消息携带的是因果依赖，接收端用本地交付向量判断是否安全释放。

## 六、全序组播

### 1. 中央 sequencer

所有消息先到定序器，定序器分配序号，再广播给组成员。优点是简单、顺序直观；缺点是中心故障和性能瓶颈。

### 2. 分布式三阶段

1. 每个节点提出 proposal；
2. 取最大 proposal 作为最终序号；
3. 消息变成 deliverable，按 FINAL_TS 交付。

临时队列不能只按当前 proposal 交付，因为后来者可能提出更大的序号。

### 3. 顺序层次

从弱到强可讲：

FIFO ⊆ causal order ⊆ total order（具体包含关系要结合故障和交付定义说明）。

全序更强，但控制消息和等待更多；不要把“更强”直接等同于“更好”。

## 七、组通信与传播树

### 1. Propagation tree

当多个组共享大量成员时，先构造 meta-group，再在 meta-group 上建立共享树，能够减少重复转发。讲图时区分：

- 普通组；
- meta-group；
- primary meta-group；
- 消息到达某个分支后继续向子树传播。

### 2. Steiner tree 与 delay bound

普通 Steiner tree 只追求低成本；delay-bounded Steiner tree 还要求源到每个目的地的时延不超过 Δ。

给例子：s 到 u、v 的链路成本低，但经过 u 的路径会使 b 的延迟超过 Δ。此时必须选择看起来更贵但满足时延约束的边。

## 八、课堂互动

1. 给四条消息构造 crown 关系图并找环；
2. 两个进程互相 send，按优先级规则排除死锁；
3. 给 DELIV 向量判断 RST 消息是否可交付；
4. 比较 sequencer 与三阶段全序的故障点；
5. 给 8 个 GPU 的 cost/delay，选择普通 Steiner 或受限 Steiner。

### 收束句

> 消息顺序决定了系统能够观察到什么；同步消息决定了异步 runtime 能否安全模拟同步程序；组通信则把“一个消息如何排序”提升为“所有目的地是否看到同一个历史”。

## 九、消息事件的边界

把 arrival、receive 和 delivery 分成三个事件：消息进入缓冲区，不等于协议取出，更不等于应用已经观察到。FIFO、因果和全序通常约束 delivery。RST/KS 的教学伪代码还隐含可靠交付、单调序号和可去重；若允许丢失、重启或重复，必须增加重传、持久化和 epoch。中心 sequencer 故障后也不能只换进程继续编号，需要任期/epoch 和状态转移。
