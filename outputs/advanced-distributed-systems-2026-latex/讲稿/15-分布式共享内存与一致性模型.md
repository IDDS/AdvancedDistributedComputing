# 第 15 讲：分布式共享内存与一致性模型

## 一、本讲定位

DSM 对应用提供共享地址空间，底层仍需要缓存、复制、失效、消息和一致性协议。本讲重点是区分 coherence 与 consistency，并把它们映射到缓存、参数服务器、KV Cache 和流处理。

## 二、DSM 抽象

应用看到对象 x 可以被多个进程读写；系统负责定位、复制和同步。优点是编程简单、读操作本地化；代价是写冲突、失效广播和一致性延迟。

先问学生：如果两个副本都缓存 x=0，P1 写 1、P2 写 2，最终值是什么？答案取决于一致性模型和冲突规则。

## 三、Coherence 与一致性模型

### 1. Linearizability

每个操作看起来在一个全局原子时刻生效，并且遵守真实时间顺序。适合锁、计数器和单对象强一致 API，但代价高。

### 2. Sequential Consistency

所有进程的操作可以排成一个顺序，同时保持每个进程自己的程序顺序；不一定保持真实时间顺序。

### 3. Causal Consistency

有因果关系的写操作按同样顺序被观察；并发写可以有不同顺序。适合社交消息、协作和部分缓存场景。

### 4. 反例

P1：write(x=1)；read(y)  
P2：write(y=1)；read(x)

若两个读取都看到 0，可能违反顺序一致性；让学生尝试构造一个合法的全局顺序。

## 四、复制与缓存

### 1. 全复制与部分复制

全复制读快但写失效成本高；部分复制减少空间和广播，但访问可能远程。

### 2. 写失效协议

写者获得许可，更新本地副本，向其他副本发送 invalidate；读者失效后重新获取。必须说明旧副本如何防止复活：使用版本号、epoch 或 lease。

### 3. 总序广播

若所有写操作经过全序广播，副本按同一顺序应用，可实现较强一致性；代价是排序点和故障恢复。

## 五、现代系统映射

- 分布式缓存：选择强一致、读后最终一致或 session consistency；
- 参数服务器：同步 step 等待所有梯度，异步更新可能产生 stale gradient；
- LLM KV Cache：缓存内容按请求前缀共享，迁移时需要路由和版本边界；
- Flink：checkpoint barrier 和 watermark 分别表达状态一致边界与事件时间进展。

## 六、库存扣减完整例子

两个副本各有库存 10：

1. P1 在副本 A 扣 7；
2. P2 在副本 B 扣 6；
3. 若异步复制，两边都认为成功，产生超卖；
4. 若 quorum 写或线性化服务，第二个操作被拒绝；
5. 若最终一致，可能先接受，之后冲突合并或补偿。

让学生比较每种语义的用户体验和系统代价。

## 七、参数服务器与 AI 训练

同步 SGD：

- worker 计算梯度；
- server 等待所有 worker；
- 聚合后更新参数；
- 广播新版本。

异步 SGD：

- worker 读取可能旧的参数；
- 提交梯度；
- server 立即更新；
- worker 继续下一步。

说明 stale gradient 会提高吞吐但影响收敛，需要用 staleness bound 或学习率调整。

## 八、Quorum、read repair 与冲突合并

若读 quorum 为 R、写 quorum 为 W，常见安全条件是 R+W>N 或读写集合相交。read repair 在读到不同版本时修复旧副本。

LWW 简单但可能丢更新；CRDT 通过可交换、可结合、幂等的合并操作减少冲突，但不适合所有业务。

## 九、课堂互动与收束

- 给一段读写 trace，判断线性化、顺序一致或因果一致；
- 计算 quorum 是否相交；
- 判断一个 stale gradient 是否可接受；
- 为模型缓存、库存、日志分别选择一致性契约。

收束句：

> 一致性不是一个越强越好的开关，而是应用对读写历史提出的契约；系统设计的任务是让契约、成本和故障恢复相互匹配。
