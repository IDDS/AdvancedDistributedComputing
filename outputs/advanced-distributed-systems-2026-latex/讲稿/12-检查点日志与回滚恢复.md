# 第 12 讲：检查点、日志与回滚恢复

## 一、本讲定位

本讲从“记录状态”推进到“失败后恢复”。重点是 orphan message、domino effect、协调/非协调检查点、通信诱导检查点、日志型恢复，以及 AI 训练的全局 checkpoint。

## 二、恢复的核心条件

局部检查点不能任意组合。若恢复状态包含消息接收，却没有包含对应发送，就产生 orphan message；若某个进程回滚后，其他进程已经依赖它的输出，就需要继续回滚，形成 domino effect。

板书：

恢复线必须是因果一致的；任何恢复后的外部状态都不能依赖被丢弃的历史。

## 三、非协调检查点

每个进程独立保存检查点，运行期开销小，但恢复时需要追踪消息依赖。

完整反例：

- P1 在 C1 后发送 m1；
- P2 收到 m1 后在 C2 保存状态；
- P2 又发送 m2；
- P3 保存 C3；
- P1 回滚到 C0，m1 消失；
- P2 的 C2 变成 orphan，必须回滚；
- P3 又依赖 m2，继续回滚。

这就是 domino effect。

## 四、协调检查点

协调器让多个进程共同建立恢复线。阻塞式协议简单但会暂停应用；非阻塞式协议允许继续执行，却必须记录 marker、边界和延迟消息。

FIFO marker 的讲法与第 4 讲 Chandy–Lamport 相连：marker 划出一个一致边界，消息落在边界前后决定是否进入 checkpoint。

Koo–Toueg 两阶段思想可以讲为：

1. 询问并准备；
2. 所有参与者确认后提交 checkpoint；
3. 任何失败则取消或重新尝试。

## 五、通信诱导检查点

通信诱导方法不让所有进程同步保存，而是根据应用消息中的因果元数据，判断接收者是否必须强制保存。

核心问题：如果某进程会在未来依赖这条消息，当前状态是否已经有安全恢复点？若没有，就在接收前强制检查点。

## 六、日志型恢复

### 1. PWD 假设

Piecewise Deterministic 应用在给定状态和输入事件后确定性执行。只要保存检查点和非确定性事件，就能重放。

### 2. 三类日志

- 悲观日志：事件先写稳定存储再继续，恢复简单、运行慢；
- 乐观日志：先继续执行，故障时补写或回放，性能好、恢复复杂；
- 因果日志：记录事件依赖，按因果边界重放。

## 七、AI 训练恢复

训练 checkpoint 不只是模型权重，还应包含模型参数、优化器状态、学习率调度器、数据迭代器位置、随机数状态、梯度累积状态、worker/world size，以及通信和分片元数据。

如果每个 worker 各自保存，可能出现：

- worker A 保存 step 100；
- worker B 仍在 step 99；
- optimizer state 与模型不匹配；
- 数据迭代器重新读取导致重复样本。

因此需要全局恢复线或分布式 checkpoint 协议。可联系 PyTorch Distributed Checkpoint/FSDP：分片保存提高吞吐，但恢复时必须重新构造一致的全局分片映射。

## 八、完整例子

三进程历史中同时放入 orphan、lost 和 delayed 消息，让学生选择恢复线：

1. 先标出每个 checkpoint 已经看到的消息；
2. 找出接收但没有发送的 orphan；
3. 找出发送已经存在但恢复后不再可见的 lost message；
4. 选择一致恢复线；
5. 判断是否需要日志重放。

## 九、外部副作用

回滚不能撤销已经发出的邮件、扣款、模型发布或外部 API 调用。解决方案包括幂等键、事务性 outbox、补偿操作和 fencing。

## 十、课堂互动与收束

- 判断四个 checkpoint 哪些可以组成一致恢复线；
- 比较协调、非协调、日志型恢复；
- 设计训练任务的 checkpoint manifest；
- 讨论一个“半个 checkpoint”为什么危险。

收束句：

> 恢复不是把文件读回来，而是把系统重新放入一个没有悬空因果依赖、可以继续执行的全局状态。
