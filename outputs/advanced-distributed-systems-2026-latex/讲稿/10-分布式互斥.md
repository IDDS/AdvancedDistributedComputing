# 第 10 讲：分布式互斥

## 一、本讲定位

临界区可以代表数据库写入、元数据更新、GPU 独占、模型发布窗口或一次迁移权。本讲比较四条路线：全序请求、回复许可、quorum 和 token。

先写三条性质：

- 互斥：最多一个进程在临界区；
- 无饥饿：持续请求者最终进入；
- 有界等待：等待时间有上界或可排序。

还要同时讨论消息数、延迟、故障恢复和公平性。

## 二、Lamport 互斥

### 1. 数据结构

每个进程维护逻辑时间和请求队列。请求以（时间戳，进程 ID）排序。

进入条件：

1. 自己的 REQUEST 已放入所有进程队列；
2. 自己请求在本地队列最前；
3. 已收到所有其他进程对该请求的确认。

### 2. 三进程例子

P1 请求（5,1），P2 请求（4,2），P3 请求（6,3）。全序为 P2、P1、P3。P2 先进入；P2 退出并广播 RELEASE 后，P1 才能进入。

强调：时间戳不是现实时间，而是确定请求顺序的逻辑标签。

## 三、Ricart–Agrawala

收到请求时：

- 若自己不请求或对方优先，则立即回复；
- 若自己请求且自己的请求更早，则延迟回复；
- 退出临界区时回复所有延迟请求。

它不需要额外 RELEASE 广播，因为回复本身就表示许可已经释放。消息数从 Lamport 的约 3(n−1) 降到约 2(n−1)，但仍依赖所有正确进程回复，因此对故障敏感。

课堂上让学生解释：为什么两个进程不能同时认为对方已许可？因为至少有一个方向的回复被延迟。

## 四、Quorum 与 Maekawa

### 1. Quorum

每个进程只向自己的 quorum 请求许可，任意两个 quorum 相交。冲突请求必然在交集成员处相遇，由同一个成员决定先后。

### 2. 死锁

Maekawa 的代价是一个成员一次只能把票投给一个请求。若 P1、P2、P3 各持有部分票，并互相等待交集票，就会形成等待环。

完整四步：

1. 各请求者拿到部分票；
2. 每个请求者还缺一个交集成员；
3. 交集成员已经把票给另一个请求；
4. 所有人等待，形成死锁。

解决方法包括优先级撤销、失败检测和请求重排序。

## 五、Token 算法

唯一 token 直接携带进入权，安全性直观：没有 token 不能进入。

但系统必须处理：

- token 丢失；
- token 重复；
- token 持有者崩溃；
- token 路径过长；
- 成员变化。

Suzuki–Kasami 使用请求序号和 token 队列。每个进程记录自己看到的请求序号，token 持有者按队列服务请求。

## 六、Raymond 树算法

令牌沿树路径传输。节点保存 holder 指针和请求队列：

1. 请求者把请求沿 holder 路径向 token 位置转发；
2. 中间节点把请求加入队列；
3. 持 token 节点把 token 沿路径传回；
4. 进入临界区，退出后服务下一请求。

消息复杂度与树距离相关，通常远小于全广播；代价是树维护和故障恢复更复杂。

## 七、AI 资源映射

- GPU 独占分配：一次训练任务拿到一组 GPU 后，其他任务不能抢占；
- 模型发布：同一模型别名只能由一个控制流程切换；
- 分片迁移：同一 shard 的 owner 变更需要互斥；
- KV Cache 重平衡：迁移窗口内避免读写冲突。

提醒：GPU 互斥还需考虑租约过期、进程死掉但 GPU 未释放、节点 fencing 和控制面一致性。

## 八、完整推演与互动

1. Lamport 三进程请求队列；
2. Ricart–Agrawala 延迟回复；
3. Maekawa 死锁环；
4. token 丢失后的恢复；
5. Raymond 树上的请求路径；
6. 选择一个 AI 资源问题，判断应该使用 quorum、token 还是全序请求。

收束句：

> 分布式互斥不是“把锁搬到网络上”，而是用消息、时间、交集或唯一 token 构造一个可证明的唯一进入权。
