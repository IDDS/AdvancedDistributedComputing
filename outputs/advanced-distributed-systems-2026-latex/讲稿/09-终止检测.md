# 第 9 讲：终止检测

## 一、本讲定位

学生必须区分“所有进程当前空闲”和“分布式计算真正终止”。真正终止要求所有进程处于终止状态，并且所有信道为空；只要还有一条在途消息，系统就可能再次激活。

## 二、形式化问题

定义全局终止谓词：

T =（所有进程 passive）且（所有信道 empty）

安全性：算法宣布终止时，T 必为真。  
活性：如果 T 持续为真，算法最终宣布终止。

反例：P1、P2 都显示 idle，但 P1→P2 信道中有一条 work 消息。若立即宣布终止，P2 可能重新变 active。

## 三、基于快照的检测

### 1. 直觉

把终止检测转为一致全局状态问题：记录所有进程的 passive 状态和所有信道状态，若所有信道为空，即可宣布。

### 2. 标签

使用标签（epoch，round）区分不同检测尝试。检测开始后，旧消息不能被误算到新快照；控制消息也必须遵守快照边界。

### 3. 证明

安全性来自一致快照：若某条 work 消息已经发送但尚未接收，它会出现在信道状态中。  
活性来自 marker 最终传播和可靠通信。

## 四、权重投掷

### 1. 核心想法

把“尚未完成的工作”编码为总权重 1：

- active 进程持有一部分；
- 发送工作消息时把权重拆出一部分随消息发送；
- 接收后再把权重纳入本地；
- passive 进程可把剩余权重归还给检测者。

如果检测者最终收回权重 1，且自己确认没有工作，就可宣布终止。

### 2. 不变量

- 权重守恒：系统总权重始终为 1；
- 权重不会凭空生成；
- 只要有未完成工作或在途工作消息，就有一部分权重尚未回到检测者。

让学生手算：检测者初始持有 1；P1 发送任务给 P2，拆成 0.4 与 0.6；P2 又转发 0.2；最终 P2 完成并归还 0.2，P1 归还 0.4，检测者收回 1。

## 五、生成树检测

树算法把全局判断拆成局部报告：

1. 根发起检测；
2. 子节点等待所有孩子报告；
3. 每个节点报告自己是否 passive、子树是否无在途消息；
4. 根汇聚所有证据。

朴素方法的竞态：节点报告 passive 后又收到新消息。解决方法是颜色 token 或 epoch：

- 白色表示本轮尚未激活；
- 黑色表示发生了向上游的反向活动；
- 根只有在收到完整的白色汇聚且没有黑色报告时才宣布。

## 六、与现代工作流的映射

- MapReduce：所有 map/reduce worker idle 还不够，shuffle 和重试消息也必须完成；
- 流处理：窗口关闭不是源头结束，必须由 watermark、源端完成标记或外部协议证明；
- AI 训练：loss 不再下降不等于作业终止，还要确认最后一个梯度、检查点、日志和控制消息完成。

## 七、完整推演

三进程工作流：

1. P1 完成 map，向 P2 发送 reduce 输入；
2. P1 变 idle；
3. 检测者读取 P1 idle；
4. 消息仍在 P1→P2；
5. P2 收到后激活并开始 reduce；
6. P2 完成并发送结果；
7. 检测者最终收齐一致快照或权重。

要求学生指出第 3 步为什么不能宣布终止。

## 八、课堂互动与收束

- 给出一个“所有节点 idle、存在一条重试消息”的时间线，找出 false positive；
- 比较快照、权重和树算法的消息复杂度；
- 设计一个 AI 训练完成契约，列出必须收齐的证据。

收束句：

> 终止检测不是数一数有多少空闲进程，而是证明“没有任何尚未可见的工作会重新激活系统”。

## 九、终止检测的适用条件

权重式算法要求消息、进程和控制者之间的权重守恒；工程实现不能直接用有舍入误差的浮点数比较“是否恰好回到 1”。如果存在丢失、重复、重启或新的任务源，需要可靠传输、持久化计数器、epoch 或任务注册协议。Kubernetes Job 的 Completed、流处理窗口关闭和 loss 稳定都只是局部信号，不能单独推出全局终止。
